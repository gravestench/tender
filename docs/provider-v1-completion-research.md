# Provider report and adverse-event completion research

Research checked against primary provider documentation on 2026-11-24. This is an implementation map, not evidence that a merchant account has delivered any of these files or events. Tender's current `SettlementReport` accepts normalized, host-verified lines and compares them with the ledger; it does not authenticate or download provider reports, aggregate payout batches, or change funds during reconciliation. The Adyen ACH row projector is the only provider-specific report importer today. See `reconcile.go`, `providers/ach/report.go`, `webhook/adyen.go`, and `providers/paypal/webhook.go`.

## Cross-provider ingestion boundary

1. The host obtains a report through its merchant-authenticated channel and retains the original bytes, delivery metadata, configuration, and a digest. Parse by named headers where the format permits configurable columns. Reject duplicate mandatory headers, malformed decimals, truncated files, duplicate financial row identities, and changed content under an existing report identity. Scope every identity to Tender environment, provider, merchant account, and report period or batch. A filename alone is insufficient for a multi-account or regenerated file.
2. Keep provider report entries and payout movements distinct. A purchase, refund, fee, reserve, correction, and payout are different financial events even if in one batch. Do not turn a payout debit into a customer refund. Preserve unmapped journals for a discrepancy queue, rather than silently dropping them from payout arithmetic. Reconcile totals and bank deposits separately from per-payment matching.
3. Tender's normalized `SettlementLine` requires `NetMinor = GrossMinor - FeeMinor`, one currency, an original provider reference, and one of four kinds. A provider's signed **fee movement** must be converted to that convention; an independent account fee, currency conversion, hold, or payout cannot necessarily fit one line. Extending the ledger/report model is necessary for a complete payout proof. Do not claim payout equality from matched transaction rows alone.

## Adyen Settlement details report

Source: [Settlement details report, standard columns, journal entries and filenames](https://docs.adyen.com/reporting/settlement-reconciliation/transaction-level/settlement-details-report/), [transaction-level reconciliation example](https://docs.adyen.com/reporting/settlement-reconciliation/transaction-level/).

| Concern | Documented fields and interpretation | Mapper consequence |
| --- | --- | --- |
| Scope and identity | `Merchant Account`; `Batch Number`; generated report name may encode a batch, date range, and an eight-character identifier for multiple accounts. A report can include selected or all merchant accounts. | Authenticate download, then scope each row to the configured merchant and batch. Use artifact identity plus digest; an account/batch pair is not a unique row key. |
| Payment/correction correlation | `Psp Reference` is the original payment PSP; `Merchant Reference` is the merchant's original reference. `Modification Reference` is the modification PSP for `Settled`, `Refunded`, and `Chargeback` (for a chargeback it can equal the capture reference). `Modification Merchant Reference` is optional. | Match original payment using the original PSP and merchant reference, then match a capture/refund operation using its modification reference when available. Do not assume the modification PSP is distinct for chargebacks. Partial captures/refunds need operation-level sums. |
| Method | `Payment Method` is the payment method brand or type (the official example uses `visa`). | The current ACH projector explicitly requires `ach`; a card mapper must accept configured card brands and must never classify a card `Settled` row as an ACH debit. |
| Money | `Gross Currency`, `Gross Debit (GC)`, `Gross Credit (GC)`, `Net Currency`, `Net Debit (NC)`, `Net Credit (NC)`, and fee columns including `Commission (NC)`, `Markup (NC)`, `Scheme Fees (NC)`, `Interchange (NC)`. A `Settled` example has gross credit and smaller net credit. | Parse decimal values exactly; credit is merchant-positive and debit merchant-negative. Require same currency before projecting a single Tender line. The difference between signed gross and signed net yields Tender's signed `FeeMinor`; keep the fee-component columns as audit evidence and check consistency where present. |
| Payout | `MerchantPayout` has a net debit; its `Modification Reference` contains the account, batch, and `TX...XT` bank-statement payout reference. Report also includes separate `Fee`, `DepositCorrection`, `ReserveAdjustment`, and `InvoiceDeduction` entries. | Link transaction/correction entries by account and batch to the payout; compare the report's payout movement with the bank statement using the `TX...XT` reference. These entries must not be forced into a per-payment line. |

`Settled` is a settlement journal, not proof that a card's authorization or capture webhook alone settled. `Refunded` and `Chargeback` are negative financial movements; `ChargebackReversed`, `SecondChargeback`, `RefundedReversed`, `SettledReversed`, and other corrections need explicit signed direction and lifecycle handling. The current ACH `ApplySettlement` has additional signed-event requirements particular to bank debits; do not copy its whole-payment assumptions into cards. Source: [Adyen journal types](https://docs.adyen.com/reporting/settlement-reconciliation/transaction-level/settlement-details-report/) and [webhook types](https://docs.adyen.com/development-resources/webhooks/webhook-types/).

**Unknowns and merchant gate:** The exact card brand set, fee arrangement, batch schedule, settlement currency, optional column configuration, report permissions, and real account payout rows must be verified in a merchant export. Adyen requires merchant report access; report generation can be configured per account/date/batch. A local parser can be built from the documented columns and official sample, but a live payout match cannot be claimed without authenticated reports and a bank statement.

## PayPal Settlement SFTP report

Sources: [Settlement report specification](https://developer.paypal.com/reports/settlement/), [T-code reference](https://developer.paypal.com/reports/reference/t-codes/).

| Concern | Documented fields and interpretation | Mapper consequence |
| --- | --- | --- |
| Artifact identity | Single-account filename `STL-yyyymmdd.sequenceNumber.version.format`; Multiple Account Management filename adds `reportingWindow` and `totalFiles`. Files can split at one million records. `RH` gives generation time/window/account/version; `SH` scopes an account section; `FH`, `SF`, `RF`, and `RC` provide file/section/report counts and currency totals (some absent in version 001). | Parse the complete file set for a date/window/version before declaring a report complete. Match header identity to filename and configured account; validate all available counts and totals. Report ID includes account, date/window, version, and full multipart set/digest. |
| Row identity and correlation | `SB.transaction_id` is a PayPal-generated money-movement event ID and may be blank; `invoice_id` is merchant-supplied and may be blank; `paypal_reference_id` plus `paypal_reference_id_type` (`ODR`, `TXN`, `SUB`, `PAP`) points to a related object; `transaction_event_code` is the T-code. | Use the combination of section/account, event ID when present, T-code, completion date, related reference, and source row position for immutable row identity. Correlate to Tender's stored capture/order reference, never by invoice alone. The current Orders v2 adapter stores `custom_id` on a purchase unit, but does not set an `invoice_id`; a real report must establish which references PayPal emits for its captures/refunds. |
| Money | `transaction_debit_or_credit` is `CR`/`DR`; `gross_transaction_amount` is unsigned minor units. `fee_debit_or_credit` separately signs unsigned `fee_amount`. `gross_transaction_currency` and `fee_currency` can differ. There is no per-row net column. Nontransactional handling fees appear as gross without a transaction fee entry. | Signed gross is `CR` positive / `DR` negative; signed fee movement is likewise `CR` positive / `DR` negative. For same-currency transaction fees, Tender `FeeMinor = -signed_fee_movement` and `NetMinor = signed_gross + signed_fee_movement`. Do not treat all `DR` rows as refunds or assume all fee amounts are costs. Reject cross-currency line projection until conversion is modeled. |
| Classification and payout | T-codes classify event type, while direction still depends on account perspective: e.g. `T0006` Express Checkout payment, `T1107` payment refund, `T1106` PayPal-initiated payment reversal, `T1201` chargeback, `T1202` chargeback reversal, `T0400` general withdrawal to bank. `bank_reference_id` is present for debits and appears on the merchant bank statement. | Use an allowlist of event codes **and** expected direction; preserve all others for review. A withdrawal (`T0400`) is a payout movement, not a customer refund. Compare account section totals and final withdrawal/bank reference separately from payment entries. |

The T-code reference explicitly warns that codes may change. The Settlement report may include holds, reserves, nontransactional fees, disputes, corrections, and multiple currencies. A complete account balance or bank payout proof requires those categories, not just Tender's four payment-line kinds.

**Unknowns and merchant gate:** PayPal requires an approved merchant and an SFTP account to obtain this report. The actual report version, reporting window, MAM structure, transaction code mix, capture/refund cross-references, and payout bank reference must be checked in merchant data. The documented schema can support fixture parsing now; SFTP delivery and real payout validation require merchant access.

## Klarna Settlement Reports

Source: [Settlement files: summary, detail and lifecycle examples](https://docs.klarna.com/acquirer/klarna/after-payments/settlements/settlement-files/), [Settlements API](https://docs.klarna.com/acquirer/klarna/api/settlements/).

| Concern | Documented fields and interpretation | Mapper consequence |
| --- | --- | --- |
| Payout identity | Summary has `merchant_id`, `payment_reference` (unique payout reference visible on bank statement), `settlement_currency`, `payout_date`, and `merchant_settlement_type` such as `NET`, `GROSS`, or `GROSS_FEE`. Reports are available by Partner Portal, Settlements API, or SFTP in CSV/PDF/JSON. | Scope to merchant ID and payout reference, with source artifact/version/digest. Use the summary payout reference for bank comparison; a same-day date is not enough. |
| Summary totals | `total_sale_amount`, `total_fee_amount`, `total_return_amount`, `total_reversal_amount`, `total_settlement_amount`, plus commission, holdback, repay, release, fee correction, and tax totals. Gross settlement can invoice fees separately; a `GROSS_FEE` settlement can be fee-only. | Do not assume `sale - fee - return` equals every payout. Validate all summary components for the settlement type and model separate account movements. |
| Detail correlation | `type`, `detailed_type`, `amount`, `order_id`, `capture_id`, `refund_id`, `merchant_reference1/2`, `posting_currency`, `merchant_capture_reference`, `merchant_refund_reference`, `capture_date`, and `reversal_reference` identify lifecycle rows. Some columns depend on report configuration. | Match a sale to Tender's captured order and specific capture ID. Group fee rows with that capture ID; match a merchant refund by refund ID and related order/capture. Multiple captures of one order are separate. Persist raw row identity, not only `order_id`. |
| Row semantics | `SALE/PURCHASE` is positive and keyed by capture ID. `FEE/PURCHASE_FEE_FIXED` and `FEE/PURCHASE_FEE_PERCENTAGE` are negative and share capture ID. `RETURN/PURCHASE_RETURN` is negative and keyed by refund ID; `FEE_REFUND/PURCHASE_FEE_PERCENTAGE_REFUND` is a separate credit. `RETURN/PAYMENT_DEFAULT` is not a merchant refund. `REVERSAL/REVERSAL` uses refund ID plus reversal reference. Holdback, release, corrections, dispute fees, and commission also occur. | Combine sale and associated fees only when identifiers and currency agree. Keep refunds, defaults, reversals and account adjustments distinct. Unmapped categories must affect payout review without changing customer operation state. |

Klarna's documented examples cover several acquiring products; Tender's adapter is scoped to Klarna Payments in US/USD. Do not assume a card-specific sample row or fee applies to that product. The default report may omit columns such as refund ID and card-specific fields; use the Report Configurator only after inspecting the merchant's actual export.

**Unknowns and merchant gate:** The merchant's report format, enabled detail columns, settlement type, payout timing, fee contract, and whether the configured Klarna Payments account has the necessary API/SFTP/Portal access remain unverified. The report schema supports parser fixtures now; actual order/refund/payout matching requires merchant exports.

## Signed adverse-event handling

### Adyen Standard notifications and dispute configuration

Sources: [webhook event meanings](https://docs.adyen.com/development-resources/webhooks/webhook-types/), [dispute webhook references](https://docs.adyen.com/risk-management/disputes-api/dispute-notifications/), [additional webhook settings](https://docs.adyen.com/development-resources/webhooks/webhook-types/additional-settings/), [Standard HMAC verification](https://docs.adyen.com/development-resources/webhooks/secure-webhooks/verify-hmac-signatures/).

The Standard HMAC covers the prescribed `pspReference`, `originalReference`, `merchantAccountCode`, `merchantReference`, amount value/currency, `eventCode`, and `success`. Tender's receiver persists these signed fields. `additionalData.disputeStatus`, `reason`, and event time are not in that signed tuple and must not independently drive funds or decide a dispute outcome.

| Code | Documented meaning | Safe next step |
| --- | --- | --- |
| `CHARGEBACK` | Funds deducted; dispute PSP in `pspReference`, original payment PSP in `originalReference`. | Correlate signed merchant account, original PSP, amount and currency; hold fulfillment and record distinct dispute/debit. Reconcile chargeback report row. |
| `CHARGEBACK_REVERSED` | Defense is provisional; a second chargeback is possible. | Record provisional credit/review, not permanent win. Enable Adyen's **Include originalReference for CHARGEBACK_REVERSED** setting or otherwise fetch a trusted dispute-to-payment link; do not infer it from an unsigned field. |
| `SECOND_CHARGEBACK` | Issuer rejects defense and deducts amount again. | Model a second debit tied to dispute PSP and original payment; do not double-subtract an identical retransmission. Adyen has settings to include the original reference for some dispute events. |
| `REFUND` | Outcome of the refund request, not final bank-cleared refund. | Continue binding it to the reserved refund operation; do not use success alone as a settlement line. |
| `REFUND_FAILED` | Refund rejected by scheme. | Hold/review the refund; compare its original payment PSP and modification PSP with the original operation and report. |
| `REFUNDED_REVERSED` | Refunded amount returned to Adyen's account. | Reverse only the affected refund movement after correlation and report confirmation; do not treat as a new sale. |
| `SETTLED_REVERSED`, `REFUND_NOT_CLEARED` | Later correction events, available only when enabled for applicable settlement flow. | Record separate correction and reconcile against report; do not assume every merchant receives them. |

`webhook/adyen.go` currently processes the card operation codes but returns unsupported for card chargebacks and these later corrections; ACH has a separate signed chargeback path. An implementation should persist each authenticated event first, use account/environment/reference/amount/currency plus the existing operation and payment to correlate, and leave ambiguous events pending for review. A webhook alone should not assert bank payout.

### PayPal verified webhook events

Sources: [webhook signature postback and event example](https://developer.paypal.com/api/rest/webhooks/rest/), [checkout event subscription and pending/denied semantics](https://developer.paypal.com/platforms/checkout/apm/reference/subscribe-to-webhooks), [PayPal integration event list including capture refund/reversal](https://developer.paypal.com/upgrade/wps/guide/Partner%20Integration/), [capture failure handling](https://developer.paypal.com/api/handle-payment-failures/).

PayPal's verification endpoint takes the configured webhook ID, the five transmission headers and the **original** JSON event. Tender already posts the unmodified event and accepts only `verification_status: SUCCESS`; it currently accepts and applies `PAYMENT.CAPTURE.COMPLETED` only. Subscribe to the events actually used for the merchant flow. The official checkout guidance distinguishes `PAYMENT.CAPTURE.PENDING` (funds not yet credited), `PAYMENT.CAPTURE.COMPLETED` (credited), and `PAYMENT.CAPTURE.DENIED` (capture not completed). PayPal also lists `CHECKOUT.PAYMENT-APPROVAL.REVERSED` for an uncaptured approved order, and `PAYMENT.CAPTURE.REFUNDED` and `PAYMENT.CAPTURE.REVERSED` in integration webhook guidance. A reversed approval, denied capture, refunded capture, and reversed completed capture are different outcomes and must not share one generic refund transition.

For each newly handled event, persist a minimal verified receipt keyed by webhook event ID and merchant scope, then re-read the authoritative order/capture/refund as appropriate. Require exact order ID, capture/refund ID, payee merchant ID, currency, amount, local buyer binding, and reserved operation when applying state. `resource_type`, `resource.status`, nested `supplementary_data.related_ids`, and the availability of an `up` HATEOAS link vary by event; do not reuse the completed-capture JSON shape for all types without a captured provider sample or event schema. A pending event must never trigger collection; denial or reversal after a prior collection needs an adverse review/compensation record and must preserve the original collection audit trail. Duplicate deliveries must be idempotent.

**Unknowns and merchant gate:** The exact event resource shapes and resource identifiers for the merchant's refund/reversal/denial flows, whether the merchant is eligible for relevant alternative payment methods, and authentic replay ordering require registered webhook deliveries from a merchant sandbox/live account. Offline signature and state-machine fixtures can be written, but cannot establish that PayPal delivered a particular adverse event for this merchant.

## Implementation order for v1 completion

1. Add provider report parsers with strict headers, exact money parsing, row classification, artifact integrity checks, and fixture cases from official samples. Preserve all unsupported movement types for discrepancy review.
2. Add an account/payout reconciliation layer that handles batch/section totals, separate fees and adjustments, and bank-reference evidence without conflating it with individual payments. Preserve signed report bytes and digest under scoped identities.
3. Extend adverse-event inbox processing with explicit state transitions and compensation/review records. Correlate Adyen dispute events using signed references and configured original-reference fields; correlate PayPal events with a fresh authenticated provider read.
4. Run merchant-specific gates on actual authenticated files, webhooks, provider ledger views and bank payouts. Mark each provider production-ready only for the exact flow that passed those gates.
