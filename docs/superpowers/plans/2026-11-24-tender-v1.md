# Tender v1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver an independent Go payment module, an earlier verified card pre-release for Blacktop integration, and full four-rail v1.0 after all applicable gates pass.

**Architecture:** A transactional engine coordinates provider operations and delegates wire contracts to provider packages. The consuming application mounts checkout, webhook, and simulator handlers and owns storage configuration and fulfillment. Sandbox verification exercises the same adapters against official endpoints.

**Tech Stack:** Go 1.26+, `net/http`, `database/sql` with an injected PostgreSQL driver, browser HTML and JavaScript, approved provider browser components, GitHub Actions.

**Spec:** [Tender v1.0 design](../specs/2026-11-24-tender-v1-design.md), derived from the 24 November 2026 implementation handoff.

## Global constraints

- Use `github.com/gravestench/tender` as the independent 0BSD Go module. Keep the root runtime standard-library first and omit required payment SDKs and server processes.
- Maintain the four-rail v1.0 target. US/USD, Adyen Checkout, direct PayPal, and Klarna are initial evaluation choices. ACH depends on selection of a compatible partner.
- Expose typed contextual engine operations named `Create`, `Confirm`, `Capture`, `Void`, `Refund`, `Get`, and `Reconcile`. M1 establishes exact exported signatures. Keep provider wire types private and optional operations capability-driven.
- Scope payment data, operation keys, provider references, and event identifiers by merchant and environment. Preserve financial invariants under concurrency and restart.
- Preserve strict on-page checkout. Allow documented in-page components, frames and approved in-page modals. Disable unsupported contexts and require approval for a separate popup.
- Use typed environment configuration for `MOCK`, `SANDBOX`, and `LIVE`, with explicit endpoint policy and separate credentials. Never send live requests in CI or fall back across environments.
- Track sandbox outcomes as PASS, FAIL, BLOCKED, or NOT APPLICABLE with a rationale. Provider-owned product availability, account access, and commercial approval are external gates.
- Keep Blacktop changes out of this repository. The early slice targets a single merchant with no change to Blacktop's existing multi-merchant payout path. Verify the standalone integration before changing an application.

## Review focus

- Concurrent same-key operations send one provider request. A changed fingerprint under the same key is rejected. Independent keys cannot charge the same scoped order claim twice. Task 2.
- Concurrent captures and refunds cannot collectively exceed the persisted authorized or captured amount. Task 2.
- A provider commit followed by a lost response survives a process restart and recovers under the original provider key. Tasks 2 and 3.
- Provider observations bind to the correct merchant account, payment, attempt, operation and amount. Replays, a webhook racing the HTTP response, and a timeout after verified success preserve one authoritative state and one fulfillment record. Tasks 2 and 6.
- A prohibited redirect or separate popup fails safely in the embedded consumer while required authentication remains authoritative. Task 7.

## M1. Core domain and persistence

### Task 1. Define typed money, payment state, and provider capabilities

**Files** `money.go`, `payment.go`, `provider.go`, `errors.go`, `money_test.go`, `payment_test.go`.

**Interfaces** Define `Money`, `Scope`, `Payment`, `Operation`, `Provider`, `Capabilities`, `CustomerAction`, and typed error categories. Make authorization, capture, refund, dispute/return, and settlement facts independently representable.

- [ ] Write `TestMoneyValidation` with USD minor units, zero-decimal and three-decimal currency cases, unknown codes, negative purchase amounts, integer overflow boundaries, and currency mismatch. Write `TestPaymentTransitions` for immediate capture, pending and customer-action flows, terminal outcomes, unknown operations and audited corrections.
- [ ] Run `go test . -run 'TestMoneyValidation|TestPaymentTransitions'` and confirm failures establish the missing behavior.
- [ ] Implement domain constructors, validated transitions and metadata. Distinguish unsupported, decline, validation, authentication, rate-limit, transport, and unknown-outcome errors. Preserve a sanitized provider status where supplied.
- [ ] Run `go test . -run 'TestMoneyValidation|TestPaymentTransitions'` and verify all assertions pass. Review and commit the cohesive domain change.

### Task 2. Persist and recover engine operations with a memory reference store

**Files** `engine.go`, `store.go`, `store/memory.go`, `engine_test.go`, `store/memory_test.go`.

**Interfaces** `Engine` consumes the domain/provider types from Task 1 and a contextual transaction interface. Define scoped order claims, payment lookup, and atomic operation reservation/result application. Normalize provider observations for both HTTP and webhook paths. Each observation carries account and host payment identity, relevant amount and currency, and attempt and operation references where available. The memory implementation supports the same invariants as the SQL integration.

- [ ] Write `TestConcurrentIdempotency`, `TestConcurrentOrderClaim`, `TestConflictingAmounts`, and `TestUnknownOutcomeRecovery`. Assert one provider mutation for concurrent identical requests or independent keys on the same scoped host order claim. Assert rejection of a changed fingerprint, cumulative amount limits, no conflicting mutation while uncertain, and stable provider key across recovery. Assert merchant and environment isolation.
- [ ] Run `go test . ./store -run 'TestConcurrentIdempotency|TestConcurrentOrderClaim|TestConflictingAmounts|TestUnknownOutcomeRecovery'` and confirm failures reflect missing reservation or engine behavior.
- [ ] Persist a scoped order claim, operation, exact request fingerprint, stable provider key, and state version before dispatch. Call adapters outside transactions. Use a second transaction to bind and apply observations with version and authority checks, then commit results, audit records, and outbox entries. Retry only documented safe operations with bounded context, jitter, and `Retry-After` handling. Implement authoritative query/recovery before accepting further conflicts.
- [ ] Run `go test -race ./...` and verify the concurrent and recovery cases pass. Review and commit the engine and memory store.

### Task 3. Verify durable transactions after independent process lifetimes

**Files** `store/postgres/`, `docs/storage.md`, `test/contract/storage_test.go`.

**Interfaces** PostgreSQL uses Task 2's store contract and a host-injected `*sql.DB`. Supply host-applied schema and transactional SQL for intents, attempts, operations, provider events, outbox, settlement and reconciliation.

- [ ] Write `TestPostgresRestartRecovery` and `TestPostgresConflictingOperations` against a disposable PostgreSQL database. Recreate the engine and database connection after reservation/result failure, check durable provider keys and inbox/outbox records, and race separate connections against the same money limits.
- [ ] Run `go test -tags=integration ./test/contract/... -run 'TestPostgresRestartRecovery|TestPostgresConflictingOperations'` with the documented test database configuration and confirm failures reflect the missing SQL behavior.
- [ ] Implement or document the complete PostgreSQL integration with unique scoped keys, indexed references, row locks or version fences, and atomic versioned state/outbox changes. Publish driver configuration, migration, and rollback steps. Keep test driver dependencies isolated where practical.
- [ ] Run both PostgreSQL checks in CI using a disposable database. Run `go test -race ./...` for the memory path. Review and commit the durable integration and instructions.

- [ ] Run `go test -race ./mockserver` and verify repeatable scenarios and clean shutdown. Review and commit the simulator and harness.
