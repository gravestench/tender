# US checkout provider research

Reviewed November 24, 2026. These are integration candidates based on provider documentation. No credentialed provider transactions, browser certifications or merchant-specific pricing were verified in this research.

## Decision for Blacktop

Prioritize a direct Adyen integration for US cards and USD ACH debits. Both use the same Checkout API and standard webhook format. Prototype cards with the Advanced flow and ACH with an ACH-only Sessions flow. The pinned ACH Component exposes plaintext bank data to the checkout document, making its submission path consequential. Adyen can arrange first-use consumer bank validation through giact under an Adyen contract addendum. This gives Blacktop one processor integration to operate. Merchant approval, enabled payment methods, validation terms and actual pricing must come from Adyen. No fee savings or onboarding date are established. [Checkout v72](https://docs.adyen.com/api-explorer/Checkout/72/overview) · [ACH Direct Debit](https://docs.adyen.com/payment-methods/ach-direct-debit/) · [giact enrollment](https://docs.adyen.com/payment-methods/ach-direct-debit/verification-with-giact/) · [Adyen pricing](https://www.adyen.com/pricing/)

| Method | Behavior under a no-navigation, no-popup checkout policy |
| --- | --- |
| Adyen card | Candidate for encrypted card entry, frictionless authorization and supported native in-page 3DS2 challenges. An issuer redirect makes that attempt unavailable. |
| Adyen ACH | Candidate using an ACH-only browser-to-Adyen session, in-page consent and server-side validation. Bank details enter the checkout document. Redirect behavior and data isolation need browser verification. |
| PayPal wallet | Blocked for ordinary desktop and mobile web. SDK v6 can switch presentation modes. Modal-only authentication lacks a documented cross-browser guarantee. |
| Klarna Payments | Blocked by default. The widget is inline, but Klarna normally opens a popup to authorize. Mobile guidance recommends a full-page redirect. |

### Adyen card and ACH

Pin candidate server requests to Checkout **v72** and browser Components to **6.45.2** for a reproducible first test. The test API base is `https://checkout-test.adyen.com/v72`. Production uses the assigned `https://{prefix}-checkout-live.adyenpayments.com/checkout/v72` base. Send `X-API-Key` from Go. Give the browser only the client key for its allowed origin. Bind each attempt to a merchant account, server-priced order, currency and stable idempotency key. [Checkout API and hosts](https://docs.adyen.com/api-explorer/Checkout/72/overview) · [Adyen Web release](https://github.com/Adyen/adyen-web/releases/tag/v6.45.2) · [Client-side authentication](https://docs.adyen.com/development-resources/client-side-authentication/) · [API idempotency](https://docs.adyen.com/development-resources/api-idempotency/)

**Cards.** Use the Advanced flow with `/paymentMethods`, the Card Component and `/payments`. Use only the brands returned for the configured merchant, country and currency. The component's default brand list omits Discover, so include it when the account response advertises it. Send the component's encrypted fields, browser data and origin, set native 3DS to `preferred`, and provide the required return URL. Gate every action from both `/payments` and `/payments/details` before handing it to the component. Allow only supported native 3DS2 fingerprint/challenge actions. For an issuer redirect or an unknown action, end the interactive attempt in place and offer another method. Never bypass issuer authentication. [Card Component](https://docs.adyen.com/payment-methods/cards/web-component) · [Native and redirect authentication](https://docs.adyen.com/online-payments/3d-secure) · [v72 payment request and action types](https://docs.adyen.com/api-explorer/Checkout/72/post/payments)

**US ACH.** For a consumer online debit, collect holder name, account type and debit authorization, then use the WEB entry class. The v72 API accepts encrypted routing and account numbers. However, source inspection of the pinned ACH Component shows that its first-use `formatData()` emits plaintext `bankLocationId` and `bankAccountNumber`. Forwarding ordinary Advanced-flow `onSubmit` data to Go would expose raw bank numbers. Keep that route disabled for new accounts. [Pinned component source](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/components/Ach/Ach.tsx#L15-L37) · [ACH request fields](https://docs.adyen.com/payment-methods/ach-direct-debit/api-only)

**Browser-to-provider candidate.** Have Go create an Adyen session for the server-priced order with `allowedPaymentMethods: ["ach"]`. Mount only the ACH Component with the session ID and session data, using the SDK's default Sessions submission. The pinned SDK posts the payment request to Adyen's session payments endpoint. Avoid callbacks or telemetry that send the form state to Blacktop. The component still handles raw bank fields in the merchant checkout document. If the merchant requires provider-origin isolated fields, this design needs a different collection surface. Confirm the actual destination, cookies, absence of navigation and returned merchant references in a credentialed browser trace. Save mandate evidence separately from payment data. Adyen Support must enable giact after the merchant signs the addendum and chooses its validation option. [Sessions guide](https://docs.adyen.com/online-payments/build-your-integration/sessions-flow/) · [Session method allowlist](https://docs.adyen.com/api-explorer/Checkout/72/post/sessions) · [Pinned session payment transport](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/core/Services/sessions/make-payment.ts) · [Validation prerequisites](https://docs.adyen.com/payment-methods/ach-direct-debit/verification-with-giact/)

**Money movement.** Verify standard notifications using the event item's HMAC over Adyen's prescribed field sequence. A raw-body HMAC is a different Adyen webhook format. Reconcile authorization, capture when applicable, refund, and chargeback events with the provider reference and merchant account. ACH authorization is provisional. Record a later return even after a prior success and reconcile settled amounts against settlement reports. [HMAC verification](https://docs.adyen.com/development-resources/webhooks/secure-webhooks/verify-hmac-signatures) · [Webhook event types](https://docs.adyen.com/development-resources/webhooks/webhook-types) · [ACH reversals and reports](https://docs.adyen.com/payment-methods/ach-direct-debit/)

### PayPal wallet

Candidate protocol is Orders **v2**, Payments **v2**, Notifications Webhooks **v1** and browser JS SDK **v6**. Go obtains a server OAuth client-credentials token at `/v1/oauth2/token` on `api-m.sandbox.paypal.com` or `api-m.paypal.com`. Create an order at `/v2/checkout/orders` and bind the returned ID to Blacktop's order. After buyer approval, capture server-side and verify capture status, amount, currency and payee. Use `PayPal-Request-Id` on supported mutations. Verify events via `/v1/notifications/verify-webhook-signature` with the configured webhook ID, transmission headers and received event. Reconcile capture completion, pending, denial, refund and reversal. [Orders v2](https://developer.paypal.com/api/orders/v2) · [REST authentication](https://developer.paypal.com/api/make-api-requests) · [Webhook verification](https://developer.paypal.com/api/rest/webhooks/rest/)

The provider-hosted browser script is `/web-sdk/v6/core` on `www.sandbox.paypal.com` or `www.paypal.com`. In the one-time payment session, `auto` tries a popup first. PayPal recommends `modal` for WebViews only and warns that desktop cookie restrictions interfere with login. PayPal recommends `redirect` for mobile. SDK documentation permits fallback if the requested mode is unavailable, and `autoRedirect.enabled` applies only to redirect mode. **Leave ordinary web wallet checkout unavailable** until a provider-supported path can enforce the site's policy in each supported browser. Permission for a specific popup would still require verifying that no full-page fallback can occur. [SDK hosts](https://developer.paypal.com/sdk/js/set-up) · [Payment session presentation and fallback](https://developer.paypal.com/sdk/js/reference/)

### Klarna in-line Payments

Candidate protocol is direct Klarna Payments **v1**, Order Management **v1** and browser SDK `https://x.klarnacdn.net/kp/lib/v1/api.js`. Use North American hosts `api-na.playground.klarna.com` and `api-na.klarna.com`. Use the merchant's server API credential with Klarna's documented Basic scheme. Create a session at `/payments/v1/sessions`, give the shopper SDK its `client_token`, then call `init`, `load` and, only in an eligible flow, `authorize` following buyer interaction. Go creates the order at `/payments/v1/authorizations/{authorizationToken}/order` and manages captures and refunds against `/ordermanagement/v1/orders/{order_id}`. [NA hosts](https://docs.klarna.com/acquirer/klarna/get-started/integration-resilience/api-urls/) · [Authentication](https://docs.klarna.com/acquirer/klarna/get-started/integration-resilience/authentication/) · [Payments API](https://docs.klarna.com/acquirer/klarna/api/payments/) · [Order Management API](https://docs.klarna.com/acquirer/klarna/api/ordermanagement/)

Klarna's SDK guide says the **authorization step opens a popup**. Klarna controls the iframe fallback where a popup is unavailable. Mobile browsers are directed toward Hosted Payment Page for reliability. Order creation can also return a `redirect_url` when a confirmation URL was supplied. Confirm with Klarna that the proposed configuration can omit that post-order navigation before enabling even an explicitly approved popup flow. No strict-flow capability should be advertised on the strength of mounting the widget. [Checkout behavior](https://docs.klarna.com/acquirer/klarna/web-payments/integrate-with-klarna-payments/integrate-via-sdk/step-2-checkout/) · [Order confirmation redirect](https://docs.klarna.com/acquirer/klarna/web-payments/integrate-with-klarna-payments/integrate-via-sdk/step-3-create-an-order/)

For the direct Payments authorization callback, provision an unguessable, per-session HTTPS callback token, redact it from logs, and match both token and session. Persist the callback before promptly acknowledging it. Use the same server-priced create-order payload on retries and correlate the provider order ID before fulfillment. The authorization callback alone is insufficient evidence of a captured order. [Klarna callback security, retry and acknowledgment](https://docs.klarna.com/acquirer/klarna/web-payments/integrate-with-klarna-payments/other-actions/authorization-callback/)

### ACH reach and independent provider options

Nacha routes transactions to the receiving financial institution by its ACH routing number. This permits an originating provider to reach eligible checking/savings accounts at major US banks, regional banks and credit unions without Blacktop maintaining a separate connection for each bank. Account eligibility, current ACH routing details, authorization and the processor's validation outcome still determine acceptance. An instant bank-link provider's institution list describes a separate verification step. No named bank has been certified for Blacktop in this research. [Nacha routing guidance](https://www.nacha.org/news/ach-operations-bulletin-4-2024-importance-maintaining-date-routing-transit-numbers) · [Adyen account types and validation](https://docs.adyen.com/payment-methods/ach-direct-debit/)

| Independent candidate | Direct integration and outstanding qualification |
| --- | --- |
| Dwolla | Strong dedicated pay-in option if the Adyen merchant account or giact terms are unsuitable. Use `api-sandbox.dwolla.com` / `api.dwolla.com`, OAuth client credentials, and `application/vnd.dwolla.v1.hal+json`. Onboard a customer, attach and verify a funding source, then create a transfer to the merchant. Two microdeposit amounts can be collected later in a merchant form. Verify `X-Request-Signature-SHA-256` over the exact webhook body. Confirm merchant eligibility and a bank collection method compatible with Blacktop's data boundary. [Pay-in flow](https://developers.dwolla.com/docs/receive-money) · [Authentication](https://developers.dwolla.com/docs/quickstart) · [Microdeposits](https://developers.dwolla.com/docs/micro-deposit-verification) · [Webhooks](https://developers.dwolla.com/docs/working-with-webhooks) |
| Stripe ACH Direct Debit | Optional direct processor for merchants already contracted with Stripe. Candidate `api.stripe.com/v1`, `Stripe-Version: 2026-11-18.endive`, matching webhook version and server secret key. Use a USD `us_bank_account` PaymentIntent, mandate, and a merchant-owned microdeposit verification form. Confirm eligibility for the intended bank collection method. The default Financial Connections flow can require bank authentication. Verify the signed event body and handle both asynchronous success and failure. [US ACH direct API](https://docs.stripe.com/payments/ach-direct-debit/accept-a-payment?payment-ui=direct-api) · [Versioning](https://docs.stripe.com/api/versioning) · [Webhook signatures](https://docs.stripe.com/webhooks/signature) |
| Braintree ACH Direct Debit | Candidate for an existing eligible US Braintree Direct merchant processing USD. Custom JS v3 supports bank entry and micro-transfers. Network check has variable bank coverage. Sandbox enablement requires contacting Braintree. Candidate server protocol is GraphQL at `payments.sandbox.braintree-api.com/graphql` or `payments.braintree-api.com/graphql`, with Basic public/private key credentials and a date-pinned `Braintree-Version` header (documented example `2019-01-01`). Verify signed webhook form fields with the provider's parser and handle settlement/decline notifications. [Eligibility and verification](https://developer.paypal.com/braintree/articles/guides/payment-methods/ach) · [GraphQL authentication and versioning](https://developer.paypal.com/braintree/graphql/guides/making_api_calls) · [Webhook parsing](https://developer.paypal.com/braintree/docs/guides/webhooks/parse/node) · [Settlement events](https://developer.paypal.com/braintree/docs/reference/general/webhooks/transaction/node/) |

### Evidence required before merchant enablement

1. Record which merchant account, allowed origin, test credentials, webhook keys, brands, ACH method and giact option are enabled. Obtain account-specific terms for processing, validation, returns and minimums before comparing cost.
2. Run a credentialed test purchase with each enabled card brand and exercise frictionless approval, native challenge, redirect-required and refusal. Instrument top-level URL changes and new windows on desktop and mobile. Confirm blocked actions leave the order unpaid.
3. Exercise ACH validation success and refusal, debit submission, delayed completion, return, duplicate webhook and refund where supported. Compare provider references and amounts to reports. Confirm that captured requests, logs and order storage contain no raw account numbers or card data.
4. If PayPal or Klarna obtains a provider-supported policy-compatible flow, test login, account recovery, cookie restrictions, blocked popups, cancellation and fallback on supported devices before exposing it. Sandbox evidence establishes the tested path only. Obtain provider approval for production and confirm production configuration separately.
