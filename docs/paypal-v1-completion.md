# PayPal v1.0 Completion Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task by task. Keep each financial transition behind a red/green test and an independent review.

**Goal:** Complete direct-merchant PayPal refund settlement, bank payout, and post-capture event correlation without inferring money movement from an unverified or ambiguous identifier.

**Architecture:** Keep PayPal report ingestion host-authenticated and separate from the Orders/Payments API adapter. Join provider report rows and verified webhook events to the scoped Tender payment through explicit capture, refund, order, seller, amount and currency references. Persist uncertain rows and receipts for review; retain `ErrUnsupported` until the selected merchant's actual artifacts prove the documented variant and field identities.

**Tech stack:** Go 1.26, Tender's `SettlementReport`/`PayoutLine` and verified inbox/adverse review contracts, PayPal Orders v2/Payments v2, Settlement SFTP and Balance Reconciliation CSV reports, PostgreSQL contracts and the loopback PayPal fixture.

**Spec:** [Tender v1 completion roadmap](superpowers/plans/2026-11-25-tender-v1-completion.md), Task 16; [provider research](provider-v1-completion-research.md).

## Current boundary and verified sources

The current adapter creates one `CAPTURE` intent order, stores its order ID as the payment reference, and stores the succeeded capture and refund IDs on their operations. `ProjectSettlement` handles only version `001` merchant-credit `T0006` rows that directly reference an `ODR` order. `T1107`, payout rows and refund/reversal webhooks return unsupported or are not subscribed. `PAYMENT.CAPTURE.PENDING`, `COMPLETED`, and `DENIED` are postback verified and correlated to a fresh order; the documented denied event has `resource.status=DECLINED`. See [PayPal provider notes](providers/paypal.md) and the [official denied payload](https://developer.paypal.com/platforms/checkout/apm/pay-upon-invoice/integrate-pui-partners).

PayPal's [Settlement report specification](https://developer.paypal.com/reports/settlement/) defines `SB.transaction_id` as a money-movement event ID and `paypal_reference_id`/`paypal_reference_id_type` as a **related** object. Its reference table says full and partial refunds refer to the **originating settlement**. A refund's related ID therefore cannot be assumed to be the Tender order. `T1107` is a [payment refund T-code](https://developer.paypal.com/reports/reference/t-codes/). The report uses unsigned integer minor units with independent CR/DR signs for gross and fee. Version `001` lacks `FH`, `SC`, `RC` and `RF`; `SF`/`FF` still require validation. The host must verify every file/section and report currency total before marking a batch complete.

The Payments API gives a possible authenticated join: [GET refund](https://developer.paypal.com/api/payments/v2/refunds-get/) returns refund `id`, `amount`, `status`, `seller_payable_breakdown.total_refunded_amount` in its documented example, and an `up` link to a capture. [GET capture](https://developer.paypal.com/api/payments/v2/captures-get/) returns capture `id`, `amount`, `status`, `payee.merchant_id`, and `supplementary_data.related_ids.order_id` when provided. These fields are optional in parts of the schema; the join must fail closed when any required field is absent. The existing adapter's refund POST/GET checks its refund ID and `up` capture link, but report ingestion does not yet perform this chain. The merchant export must establish that an `SB` refund's `transaction_id` is the Payments v2 refund ID and its related `TXN` is the capture ID for this merchant product.

For direct merchants, PayPal documents a [Balance Reconciliation report](https://developer.paypal.com/reports/balance) available by portal or SFTP. Its `RD` fields include `Merchant Account ID`, `Record ID`, `Related Record ID`, `Record Type`, `Record Subtype`, `Settlement Currency`, `Settlement Amount`, `Transfer ID`, and `Transfer Account`; `RF` identifies file number, record count and total files. `Transfer ID` is described as the identifier on the merchant bank statement. PayPal's [terminology](https://developer.paypal.com/reports/reference/terminology/) defines `Withdraw money`/`Disbursed`, and the Settlement T-code reference calls `T0400` a bank-account settlement withdrawal. The [published Balance sample](https://www.paypalobjects.com/ppdevdocs/Sample-Balance%20Report-CCOP.csv) shows card `Refund,Referenced` rows with `Related Record ID` pointing at sale IDs, but contains no `Withdraw money` row to pin withdrawal sign and amount field or establish this wallet product's exact record mix. Balance report money is in **major** units, unlike Settlement SFTP's minor units. `Transfer ID` is optional. The [Disbursement Reconciliation report](https://developer.paypal.com/platforms/reports/partner-merchant-reconciliation/disbursement-reconciliation-report/) is explicitly for embedded integrations and cannot be silently used for Tender's direct merchant adapter; the [Partner Fee Disbursement report](https://developer.paypal.com/platforms/reports/partner-financial-reconciliation/disbursement) describes partner commission, not this merchant's customer-payment payout.

PayPal names `PAYMENT.CAPTURE.REFUNDED` and `PAYMENT.CAPTURE.REVERSED` in its [partner integration webhook guidance](https://developer.paypal.com/upgrade/wps/guide/Partner%20Integration/), while the [checkout subscription guide](https://developer.paypal.com/payment-methods/webhooks/) pins pending/completed/denied capture semantics. The currently located primary pages do **not** pin the refund/reversal event's resource type, whether `resource.id` is the refund, capture or reversal ID, whether amount is per event or cumulative, or the merchant payee fields for those events. A generic capture-event parser would guess. The Payments v2 refund read and its capture `up` link are usable only after a verified event supplies an unambiguous refund ID or a local succeeded refund operation supplies it; a reversal needs its own documented identity and amount meaning.

## Trust and scoping invariants

1. Authenticate the original SFTP/portal artifact and retain its digest, report/window/version, all file numbers, section account, counts and currency totals. Never treat a single `SB`/`RD` row or an `RF` balance footer as a complete payout. The host assertion `Tender Report Complete=true` is a claim by the ingesting host, not verification by `ProjectSettlement` itself.
2. Resolve the report's encrypted account/Payer ID to the configured PayPal seller for this scope using a merchant-approved mapping; compare to authenticated `payee.merchant_id`. Never join records across seller, Tender merchant, environment or currency merely because transaction IDs match.
3. For a refund, require `SB.transaction_id == GET refund.id == succeeded local refund operation.ProviderReference`, `SB.paypal_reference_id_type == TXN`, `SB.paypal_reference_id == GET refund.up capture ID == succeeded local confirm operation.ProviderReference`, and `GET capture.supplementary_data.related_ids.order_id == payment.ProviderReference`. Match refund amount/currency to the operation; compare fee separately. The report's `invoice_id`, `custom_field`, buyer identifiers and timing alone cannot establish this join.
4. For a payout, keep withdrawal distinct from customer refund/fee/reserve. Require one authenticated direct-merchant withdrawal row with the selected report's exact record type/subtype, merchant account, currency, signed amount and nonblank bank `Transfer ID` or `bank_reference_id`; compare the independent bank deposit reference and amount. Normalize provider account debit to merchant-positive payout. A bank reference absent or reused across unrelated payouts leaves the result open.
5. For a webhook, verify PayPal's signature postback against the original JSON before storing a minimal receipt. Re-read the exact resource through a merchant-bound token outside the transaction; compare all scoped IDs, amount, currency and local operation/ledger state inside the receipt transaction. A post-capture unknown refund/reversal creates sealed review work, never erases prior fulfillment or asserts principal. Duplicate and reordered deliveries must be idempotent.

## Sequential implementation slices

### Slice 1: Authenticate the refund reference chain

**Prerequisite:** A sanitized merchant `T1107` full and partial refund row, authenticated GET refund/capture responses, and local succeeded operations establish the report `transaction_id`/`TXN` mapping above. Until then `T1107` remains `ErrUnsupported`.

- [ ] Write `TestPayPalRefundSettlementJoin` with literal partial and full refund rows and provider reads. Assert exact order/capture/refund IDs, seller/account, amount/currency, signed fee, `OriginalReference=order`, `ModificationReference=refund ID`, and `Kind=refunded`; run `go test ./providers/paypal -run '^TestPayPalRefundSettlementJoin$' -count=1` and observe the intended failure.
- [ ] Add negative subcases for a swapped capture, another seller's capture, same-amount wrong order, absent `up` link or `related_ids.order_id`, missing refund ID, wrong total, duplicate partial refund, cross-currency fee and absent succeeded local refund operation. Assert no matched settlement line and no funds/outbox mutation.
- [ ] Implement `func (a *Adapter) ProjectRefundSettlement(ctx context.Context, fields map[string]string, observedAt time.Time) (tender.SettlementLine, error)` in `providers/paypal/report.go`. It makes authenticated GET refund and GET capture calls **before** Tender's reconciliation transaction; it derives the order from the capture read, never from a caller supplied order field. `Engine.Reconcile` then checks that order and refund ID against the same scoped payment and succeeded operation. The projector cannot turn a refund into a new funds transition.
- [ ] Run the focused test, memory and PostgreSQL reconciliation contracts under `-race`, then `go test ./...` and `go vet ./...`; review and commit only slice paths.

### Slice 2: Prove one direct-merchant bank payout feed

**Prerequisite:** A complete merchant Balance Reconciliation report set containing an actual `Withdraw money`/`Disbursed` row, or a complete Settlement SFTP set containing `T0400`, plus the corresponding bank deposit. Confirm which field is the signed withdrawal amount, the transfer reference, the merchant scope, and whether multiple withdrawal rows share one bank transfer. Check all report footer counts and balance roll-forward; do not substitute an embedded/partner report.

- [ ] Write `TestPayPalDirectMerchantPayout` from the sanitized real row and bank statement reference. Assert conversion of the actual negative provider movement to positive `PayoutLine.AmountMinor`, stable payout identity, source part/section/batch, and that the bank reference matches. Observe RED before implementation.
- [ ] Test incomplete/missing multipart files, duplicate or missing `Transfer ID`/`bank_reference_id`, wrong account, multiple currencies, reserve/hold/fee adjustments, withdrawal reversal, unequal report and bank amounts, and `RF` balance footer without withdrawal. These must stay incomplete/unmatched, never a false payout match.
- [ ] Implement only the proven feed's bounded parser and `func ProjectBalancePayout(fields map[string]string, observedAt time.Time) (tender.PayoutLine, error)` in `providers/paypal/balance_report.go`, then reconcile complete batch totals and bank evidence. This pure projector consumes host-authenticated `RD` fields and host completeness/scope metadata; it must not claim to download or authenticate SFTP itself. Keep the other feed `ErrUnsupported`. Run focused race, SQL reconciliation, root tests and vet; review and commit.

### Slice 3: Correlate refund and reversal webhook resources

**Prerequisite:** Registered merchant sandbox deliveries for `PAYMENT.CAPTURE.REFUNDED` and `PAYMENT.CAPTURE.REVERSED` with original JSON, postback headers, matched Payments API reads and the corresponding original order/capture/refund records. Record exact `resource_type`, `resource.id`, status, event amount meaning and parent IDs for the merchant product before enabling intake.

- [ ] Write `TestPayPalRefundReversalWebhookCorrelation` with distinct sanitized real refund/reversal shapes and a negative fixture for each plausible wrong resource ID. Observe RED. Assert duplicate, reorder and lost provider read leave one retryable receipt and never duplicate or erase fulfillment.
- [ ] Add a refund path only if its verified event identifies a unique refund resource. Compare GET refund `id`, status, amount, `up` capture ID, local refund operation and GET capture's seller/order; decide from documented semantics whether an already succeeded refund is confirmation or an external refund requires a sealed review. A reversal must use its independently documented event ID/amount/reference, not the refund branch.
- [ ] Keep any unpinned event unsupported and visible to operators. Run focused memory/SQL `-race`, PayPal durable E2E, root tests and vet; review and commit.

## External evidence still needed

No connected merchant PayPal account, SFTP export, real payout/bank statement or registered refund/reversal delivery was available in this research. A real merchant report may use a version other than `001`, MAM account sections, a different T-code mix, a report transaction ID that does not equal the Payments v2 refund ID, or a bank transfer without the optional reference. Those variants require a new bounded mapping and tests from the actual artifact. Ordinary web PayPal checkout also remains disabled under the project's on-page presentation policy; this plan does not change that gate.
