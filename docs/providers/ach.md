# US ACH Direct Debit with Adyen

**MOCK is available for integration. Official sandbox and live checkout are BLOCKED.** The candidate covers a one-time US consumer checking or savings debit in USD, using the ACH network through Adyen with giact account validation. Merchant acceptance, bank coverage, validation outcomes and pricing require account-specific qualification. [Partner selection](../adr/0005-us-ach-partner.md) · [Eligibility and payment risks](https://docs.adyen.com/payment-methods/ach-direct-debit/)

## Set up checkout

Construct `adyen.NewACH(adyen.Config{...})` with the same endpoint and credential rules as the card adapter. Configure the engine with provider name `adyen`, the merchant account and the US/USD/`tender.MethodACH` market. Use the same SQL store and signed Standard webhook endpoint for the ACH route. Route a shared merchant's verified events to the engine for the payment's market. `NewACH` exposes zero checkout capabilities in SANDBOX and LIVE, including when the LIVE account flag is set. [Adyen endpoint configuration](adyen.md) · [Checkout v72](https://docs.adyen.com/api-explorer/Checkout/72/overview)

1. Call `Engine.Create` with the trusted order, amount and an empty token. In MOCK this POSTs to `/sessions` with an Adyen API key, the reserved idempotency key, embedded mode, US country, Web channel, Ecommerce interaction and the single allowed method `ach`. It returns an expiring component action after checking the echoed account, reference and amount.
2. Use `adapter.CheckoutSession(payment)` before rendering consent. The fixture accepts only an empty-body POST to `/mock/consent/{sessionID}/approve` or `/deny`. Its synthetic consent is for the test debit only. For the provider candidate the browser gets the session ID, session data and a public client key for the registered origin. Use the default Sessions submission. An Advanced `onSubmit` or form-state logger would expose plaintext bank numbers. The pinned ACH Component runs in the checkout document. [Component source](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/components/Ach/Ach.tsx) · [Sessions transport](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/core/Services/sessions/make-payment.ts)
3. On a synthetic receipt, call `Engine.Confirm` with the trusted amount and only the fixture's opaque `sessionResult`. The adapter exchanges it through authenticated `GET /sessions/{sessionId}?sessionResult=…`. An authorized ACH debit remains pending with zero card authorization or capture and zero collected funds. A refused or canceled session becomes declined. Adyen's session result is fixed. Read current Tender state with `Engine.Get` and use notifications and reports for subsequent updates. `Engine.Recover` does not poll the session. [Create a session](https://docs.adyen.com/api-explorer/Checkout/72/post/sessions) · [Session result semantics](https://docs.adyen.com/api-explorer/Checkout/72/get/sessions/_sessionId_)
4. A signed authorization can arrive before the result reaches the host, even after the browser closes. Its PSP then fences further consent. If `CheckoutSession` declines to expose an action and a PSP is already bound, show the unsettled debit as pending. The original action record remains available to an in-flight receipt exchange. A failed single authorization in a still-open session is insufficient evidence to terminate the entire session. Process its verified row after a definitive refusal is correlated.

## Verification and merchant consent

Adyen handles the SEC code automatically for Components. Select a personal account for the WEB consumer route. Enable ACH in the test Customer Area, execute the giact addendum, ask Support to enable the consumer ecommerce validation option, and configure Standard webhook additional settings to include bank verification results. For an eligible first payment, giact validation passes or refuses the account. The service uses its database and rules. A passed validation does not establish available funds. Adyen requires an electronically signed customer mandate with the applicable amount, frequency, account and revocation provisions. The pinned form contains account fields and a pay button. The merchant must arrange compliant mandate presentation and evidence retention before enablement. Agree with Adyen on the admissible account reference, retention and retrieval method so raw banking details stay outside Go logs, inputs and storage. [giact integration and official test cases](https://docs.adyen.com/payment-methods/ach-direct-debit/verification-with-giact/) · [Mandates and SEC codes](https://docs.adyen.com/payment-methods/ach-direct-debit/) · [Pinned rendered form](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/components/Ach/components/AchComponent.tsx)

## Settlement and returns

Mount `webhook.NewAdyen` with an ACH-configured engine, store, scope and processor account. It verifies the Standard item HMAC with the configured keys, saves only signed fields before HTTP 202 and processes the receipt transactionally. Its signed `AUTHORISATION` and `CHARGEBACK` observations correlate the session's merchant reference to the original operation, amount, account, attempt and payment PSP. Unsigned bank verification metadata and reason text stay out of this evidence. A chargeback sets gross returned on the debit. A correlated signed `CAPTURE_FAILED` clears the action, puts the debit on `capture_failed` hold and enqueues one durable host review with the original and failed capture PSPs. This includes failed automatic capture before settlement and a late notification after a prior settlement. The Standard HMAC covers the event and references, while the specific refusal reason is unsigned. Adyen lists 1063_101 for blocked accounts and 1063_201 for outdated routing. Check the Customer Area before classifying a bank account or deciding how to resolve the hold. Tender never automatically retries a held debit. [ACH blocked accounts and routing errors](https://docs.adyen.com/payment-methods/ach-direct-debit/#blocked-bank-accounts) · [Capture failure fields](https://docs.adyen.com/api-explorer/Webhooks/1/post/CAPTURE_FAILED) [Standard HMAC](https://docs.adyen.com/development-resources/webhooks/secure-webhooks/verify-hmac-signatures/) · [Chargeback notification](https://docs.adyen.com/api-explorer/Webhooks/1/post/CHARGEBACK)

A host worker downloads the authenticated merchant **Settlement details report**. Map one CSV record by header using `ach.MapSettlement`, or use `ach.ReadSettlement` for a header plus one record. Pass trusted rows to `ach.ApplySettlement` with the engine, its store, account, scope and report filename. Keep this entry point private to the report worker. The projection accepts domestic ACH `Settled` credits and `Chargeback` debits. It retains signed gross/net USD cents, batch, merchant reference, original PSP and modification reference. A batch identifies the payout group. The separate MerchantPayout line contains the bank statement payout reference. Unsupported journal types, other currencies, ambiguous directions and unmatched references require review. [Settlement details columns and journal types](https://docs.adyen.com/reporting/settlement-reconciliation/transaction-level/settlement-details-report/)

The verified inbox stores each projected report receipt. Reprocessing an identical row after restart is safe. If the browser never returned and no PSP is bound, the worker requires a matching signed authorization in the inbox before binding the report PSP. Settlement enqueues collection once. A previously received matching chargeback prevents collection even when the report worker runs first. Chargeback report processing requires a signed receipt with the same original PSP and chargeback modification PSP. A report that precedes its receipt stays pending for replay. A received, correlated capture failure also fences settlement. For a late failure, the original settlement and collection record remain auditable. The fulfillment worker must check current payment state and consume the durable capture-failure review queue, including after earlier delivery. A later return preserves the earlier gross settlement, collection record and audit history. The host owns delivery decisions, review of any already fulfilled returns and the worker that retries pending receipts. A lost session creation response before browser handoff requires operator review. This adapter advertises no capture, cancellation or refund operation. Adyen offers post-settlement bank refunds with its separate bank-refund role and delay. That modification and its interaction with returns require separate implementation and qualification. [Refund permissions and delay](https://docs.adyen.com/payment-methods/ach-direct-debit/)

## Reproduce the evidence

```sh
go test -tags=integration ./test/contract/... -run '^TestACH'
go test -tags=e2e ./test/e2e/... -run '^TestACH'
PAYMENTS_ENV=sandbox go test -tags=sandbox ./test/sandbox/... -run '^TestACH'
```

The offline contract supports a disposable local `TENDER_TEST_DATABASE_URL`. The browser suite uses Chromium and Playwright with the shared checkout origin guard. The protected official tests fail visibly when access or evidence is missing. `TestACHSandboxSessions` requires the merchant's test API key, public test client key and account in the existing `TENDER_ADYEN_*` variables, a registered HTTPS `TENDER_ACH_TEST_ORIGIN` and `TENDER_ACH_GIACT_ENABLED=1` after Support activates consumer WEB validation. The probe creates two USD 12.34 test sessions. A controlled Chromium checkout loads the pinned SDK, mounts ACH with default submission and tests Adyen's published giact pass and refusal fixtures. The browser checks the submission destination and decision and rejects a popup, top-level navigation, unexpected destination or bank fixture transmitted to the host. It sends no credentials to a bank. This exercises the controlled test surface. Actual merchant mandate presentation, privacy controls and supported desktop/mobile browser behavior still require merchant verification.

`TestACHSandboxReport` reads merchant-exported `TENDER_ACH_SETTLED_CSV` and `TENDER_ACH_RETURNED_CSV` projections, each with a header and one transaction row. Supply `TENDER_ACH_HOST_EVIDENCE` as private JSON containing `Merchant`, `Reference`, `PSP`, `SettlementModification`, `ReturnModification` and trusted positive `Minor`. Both transactions must belong to the same returned debit and account. Reconcile these records to signed notifications, a separately retained mandate, and the available Customer Area validation evidence. No official merchant run is recorded.
