# PayPal US wallet

The direct merchant adapter uses OAuth 2.0 client credentials, Orders v2 with capture intent, Payments v2 refunds and Notifications Webhooks v1. The local US/USD fixture supports buyer approval, cancellation and full capture plus partial or full refunds. SANDBOX and LIVE checkout creation and confirmation are disabled. PayPal JS SDK v6 recommends a popup-first automatic presentation, limits the modal to WebView scenarios and recommends redirect for mobile. A supported, strictly in-page desktop or mobile web flow remains **BLOCKED**. [Presentation modes](https://developer.paypal.com/sdk/js/reference/) · [Orders API](https://developer.paypal.com/api/orders/v2)

## Configuration

Use provider name `paypal`, method `tender.MethodPayPal`, country `US` and currency `USD`. Pass the same host merchant scope and processor merchant ID to `paypal.New` and `tender.NewEngine`. Configure the PayPal REST app's client ID, secret and registered webhook ID separately for each environment. The default transport disables proxies and redirects. An optional host-supplied transport must protect credentials and enforce the configured destination.

| Environment | Exact API base |
| --- | --- |
| MOCK | A loopback IP literal, optional port and optional mount path |
| SANDBOX | `https://api-m.sandbox.paypal.com` |
| LIVE | `https://api-m.paypal.com`, with explicit `LiveActivated` after merchant approval |

The adapter exchanges Basic client credentials at `POST /v1/oauth2/token`, caches the bearer until shortly before expiry and retries one definite HTTP 401 with fresh credentials. It sends the engine's durable provider key in `PayPal-Request-Id` and requests full representations. Use the engine's default UUID generator or equivalent provider-safe operation IDs and keys. Keep credentials, transmission signatures, access tokens and complete provider responses out of logs and browser state. [OAuth](https://developer.paypal.com/api/rest/authentication/) · [Idempotency](https://developer.paypal.com/api/rest/reference/idempotency/)

## Operations

| Engine operation | Provider evidence and effect |
| --- | --- |
| Create | Posts one `CAPTURE` order with the server-priced purchase unit, intended payee and PayPal wallet source. Reads the order back and checks its amount, seller, payment ID and immutable attempt reference. MOCK returns the order ID as a ten-minute synthetic component action. |
| Confirm | Accepts an empty token. Reads the stored order ID and requires `APPROVED`, the same purchase unit and a PayPal buyer account. Posts to the bound order's capture endpoint and reads the order again. A single final `COMPLETED` capture of the exact amount establishes collection. A pending capture keeps the operation open. |
| Refund | Reads the bound order and single capture, posts the requested USD amount to that capture's refund endpoint, and matches the returned refund ID, amount, merchant-controlled operation reference and parent capture link. Only completed refunds increase the refunded amount. |
| Recover | Queries the stored order after an ambiguous confirmation. A bound pending refund can be read by its refund ID. A lost create or refund response without a bound resource ID requires operator correlation. While an outcome is unknown the engine blocks new conflicting operations. |

The purchase unit carries the host's opaque payment ID in `custom_id` and a digest of the scoped order, amount, account and attempt in `reference_id`. An approved browser callback does not authorize fulfillment. Closing or cancelling the approval component leaves the order uncollected. The adapter supports capture-on-confirm only. Separate authorizations, standalone captures, voids, multiple purchase units, disputes and reversals remain outside its supported operations. A narrow host-authenticated settlement row projector is available below. [Create order](https://developer.paypal.com/api/orders/v2/orders-create) · [Capture order](https://developer.paypal.com/api/orders/v2/orders-capture) · [Order details](https://developer.paypal.com/api/orders/v2/orders-get) · [Refund captured payment](https://developer.paypal.com/api/payments/v2/captures-refund)

## Verified notifications

Mount the receiver returned by `adapter.Webhook(store, engine, onStored)` under the registered route for that merchant. Subscribe to `PAYMENT.CAPTURE.PENDING`, `PAYMENT.CAPTURE.COMPLETED`, and `PAYMENT.CAPTURE.DENIED`. The handler posts the received event, the configured webhook ID and PayPal's five transmission headers to `/v1/notifications/verify-webhook-signature` on the configured API base. It requires `verification_status == "SUCCESS"`, validates the certificate URL's environment and path, and persists only the event ID, event kind, payee, capture/order references and amount before returning HTTP 202. The handler never fetches the supplied certificate. A failed postback or failed inbox write leaves delivery unacknowledged. [Message verification and capture event example](https://developer.paypal.com/api/rest/webhooks/rest/) · [Checkout status events](https://developer.paypal.com/payment-methods/webhooks/)

Have a worker call `receiver.Process(ctx, eventID)` after notification or while draining the store's unprocessed inbox. It reads the authenticated order outside the transaction, binds the signed capture and seller to a scoped local confirmation, then atomically updates the payment, operation, receipt and fulfillment outbox. PENDING leaves funds and fulfillment unchanged. DENIED closes an uncollected confirmation; a denial after a recorded capture queues one sealed adverse review and preserves prior fulfillment. Unresolved or reordered receipts remain pending for retry or operator review. Refund and reversal webhooks are not applied until their resource IDs, amounts and parent references are independently pinned and corroborated. The fixture models the verify endpoint with a private synthetic signing key and runs over loopback HTTP. PayPal's public dashboard simulator emits mock events that cannot be verified by postback. External validation requires a webhook generated by a real sandbox transaction. [PayPal webhook simulator limitations](https://developer.paypal.com/api/rest/webhooks/simulator/)

## Host-authenticated settlement projection

`ProjectSettlement` accepts a decoded `SB` row from PayPal's Settlement SFTP report, plus host assertions from its authenticated complete report set. It currently accepts **version 001** `T0006` merchant-credit Express Checkout capture and `T1107` merchant-debit refund, with a nonblank `transaction_id` and a related `paypal_reference_id_type=ODR` order ID. The order is the original payment reference; the transaction ID is the capture or refund modification reference. The host must establish that the latter is the succeeded local operation before reconciliation can match. Rows referencing only a prior transaction (`TXN`), other T-codes, other currencies and report versions return `ErrUnsupported`. This is a narrow projection, not a generic report importer. [Settlement SFTP specification](https://developer.paypal.com/reports/settlement/) · [T-codes](https://developer.paypal.com/reports/reference/t-codes/)

PayPal expresses gross and fee amounts as **unsigned integer minor units**. `transaction_debit_or_credit` signs gross; `fee_debit_or_credit` signs the independent fee movement. Tender's `FeeMinor` is the opposite of signed fee movement and `NetMinor = GrossMinor - FeeMinor`. Fee fields may all be empty; cross-currency fees are unsupported. No buyer, invoice or consumer identifier is copied into a projected line.

Before setting `Tender Report Complete=true` on a row, the host must authenticate the SFTP file set, match every filename and sequence to the `RH` account/version and each `SH` account, verify every part and section, and check `FF`/`SF` counts and currency totals (and `FH`/`SC`/`RF`/`RC` when the version provides them). Attach `Tender Expected Merchant Account`, `Tender RH Account ID`, `Tender SH Account ID`, `Tender Report Version`, `Tender Source Part ID`, `Tender Source Section ID`, and `Tender Batch ID`. The projector checks these bounded assertions but cannot inspect all other rows or parts; retain the source artifacts and audit the host parser. For version 001, `FH`, `SC`, `RC` and `RF` are absent. Multipart source part and section IDs must follow the actual row's position. [Report structure](https://developer.paypal.com/reports/settlement/)

`ProjectPayout` returns `ErrUnsupported`, including for `T0400` bank withdrawals. PayPal documents `T0400` and an optional `bank_reference_id`, but merchant data must prove the chosen payout feed, full file set, withdrawal direction and bank correlation. An `RF` balance footer is not bank payout evidence. **PayPal payout reconciliation remains an open v1.0 gap.**

## Verification gates

The memory and PostgreSQL contracts exercise the actual adapter against the embeddable fixture, including lost-response recovery, duplicate webhooks and a single fulfillment row. The SQL contract uses a disposable local database selected by `TENDER_TEST_DATABASE_URL`. A synthetic buyer is available through the loopback-only fixture routes `POST /fixture/orders/{id}/approve` and `POST /fixture/orders/{id}/cancel` with JSON content type.

**Sandbox transaction and browser verification are BLOCKED.** Required evidence includes a merchant-owned US sandbox seller and approved REST app, separate buyer, registered HTTPS listener and webhook ID, genuine order/capture/refund records, and a documented policy-compatible checkout surface. Verify the intended seller, buyer account, currency, amount, webhook receipt and current provider state for the same order. Record desktop/mobile browser, cookie restrictions, cancellation, top-level location and popup behavior before offering a wallet action. Production also requires separate merchant activation and settlement evidence. [Sandbox accounts](https://developer.paypal.com/tools/sandbox/accounts/) · [SDK v6](https://developer.paypal.com/sdk/js/set-up/)

For the read-only sandbox proof, set `PAYMENTS_ENV=sandbox`, `TENDER_PAYPAL_CLIENT_ID`, `TENDER_PAYPAL_SECRET`, `TENDER_PAYPAL_MERCHANT_ACCOUNT`, `TENDER_PAYPAL_WEBHOOK_ID` and `TENDER_PAYPAL_SANDBOX_PROOF_FILE`. Run `go test -count=1 -tags=sandbox ./test/sandbox -run TestPayPalSandboxTransaction`. The private JSON input contains `Payment` and `Confirm` in the engine's exported record shapes, `ExpectedBuyerID`, `ExpectedCaptureID`, `Headers` as a string-array header map, and `Event` as the original transaction webhook JSON object. Use the pre-collection payment and its uncertain confirmation with the original purchase-unit binding and the operation’s pre-dispatch buyer digest. The test compares the authenticated sandbox buyer and capture, submits the original event to PayPal for verification, then checks that applying the verified delivery twice produces one outbox row. This gate needs previously generated merchant transaction evidence and does not launch a checkout.

## Run the synthetic checkout

Start the independent example consumer in MOCK with a migrated local database and host fulfillment table. Set `TENDER_CONSUMER_PROVIDER=paypal`, `TENDER_CONSUMER_DATABASE_URL` and `TENDER_CONSUMER_SCHEMA`. Open a one-use session ticket printed by the consumer. The authenticated order page offers synthetic approval and cancellation in the current document. The host supplies the amount, validates the session and CSRF token, confirms via the server adapter and projects the durable outbox to its fulfillment table. The simulator routes require a server-only, per-process credential. Synthetic approval and cancellation never contact PayPal.

Set `TENDER_PAYPAL_MOCK_PRESENTATION=popup` or `redirect` to simulate an incompatible checkout context. The page disables PayPal before reserving an order. The offline `TestPayPalCheckout` runs all three contexts in Chromium, checks top-document and window events, and compares the result with the PostgreSQL payment, receipt and fulfillment rows.

### Retry and correlation details

A transport failure while acquiring OAuth credentials or reading a prerequisite order returns `tender.ErrNotDispatched` when no financial request could have taken effect. Use `RetryCreate` with the failed reservation ID and a new key for an unsubmitted create, or a fresh confirmation/refund key for a later attempt. The adapter recognizes allowlisted, endpoint-specific PayPal validation and decline issues from bounded 400/422 responses. A definite `INSTRUMENT_DECLINED` leaves the order unpaid. A documented `403 NOT_AUTHORIZED` on an implemented mutation closes the denied attempt. The refund-specific `422 TRANSACTION_DISPUTED` fails the requested refund without increasing refunded funds. Unknown or mixed error details, already-captured reports, malformed replies and a lost financial POST require reconciliation. A duplicate fixture request returns the current state of the original resource. [PayPal error reference](https://developer.paypal.com/api/rest/reference/orders/v2/errors/) · [Validation issues](https://developer.paypal.com/api/rest/troubleshooting/rest_validation_error/) · [Orders authorization errors](https://developer.paypal.com/api/rest/integration/orders-api/errors/) · [Payments v2 refund errors](https://github.com/paypal/paypal-rest-api-specifications/blob/main/openapi/payments_payment_v2.json) · [Idempotency](https://developer.paypal.com/api/rest/reference/idempotency/)

Confirmation first commits a scoped digest of the authenticated, approved buyer to the reserved operation. A durable checkpoint failure stops the capture POST. The operation digest is write-once and survives a lost or malformed capture response, a process restart and later payment updates. Confirmation compares the approved buyer, order and purchase unit with both the capture POST representation and a new order read. The received capture ID, currency and amount must agree. Conflicting evidence leaves the confirmation pending with zero newly collected funds. The host retains a scoped digest of the approved buyer and waits for a signed capture event plus a matching authenticated read. A single disputed order read cannot clear this hold. A pending webhook received during an in-flight confirmation stays in the inbox for retry after the HTTP operation finishes its comparison. [Capture representation](https://developer.paypal.com/api/orders/v2/orders-capture)

In the independent MOCK consumer, approval and server confirmation are separate requests. If the buyer disconnects between them, reopening the same scoped order can resume an already-approved fixture. The status view reports `CaptureReceiptProcessed` after the matching durable inbox row has been processed. The Chromium test waits for this receipt and for fulfillment before closing its consumer process.

PayPal advertises `QueryAfterDispatch` and requires `ProviderRequest.BindEvidence` before confirmation can send a capture. Reference stores record the initial call deadline and whether the reservation is still waiting for its first evidence checkpoint. A worker that expires before writing that checkpoint can be replaced safely. Recovery closes its reservation as `ErrNotDispatched` in the same transaction that prevents the expired owner from sending.

After the checkpoint, a worker can still be comparing the capture POST and GET when its deadline expires. A plain GET cannot settle that reserved confirmation. A signed capture receipt and matching authenticated order may reconcile the abandoned reservation after expiry. A finisher that records an unknown outcome permits read-only recovery against the persisted buyer digest. A conflicting response still requires the signed receipt. Legacy reserved records with no deadline can use signed receipt reconciliation. Legacy records also lacking a buyer digest rely on the signed capture, scoped order and attempt binding, configured seller, wallet source, amount and currency. These records cannot attest the original buyer from historical local data. Supply matching clocks to the adapter and engine when using an injected clock.
