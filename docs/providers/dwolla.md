# Dwolla US ACH pay-in candidate

This adapter implements the documented Dwolla HAL v1 pay-in transfer wire format in MOCK. Ordinary SANDBOX and LIVE constructors advertise **no capabilities**. Dwolla is an additional US ACH processor candidate, not a qualified alternative to the Adyen/giact route and not evidence of a lower merchant cost. [Receive money](https://developers.dwolla.com/docs/receive-money) · [Transfer lifecycle](https://developers.dwolla.com/docs/transfer-lifecycle)

## Implemented offline path

`dwolla.New` binds one Tender scope, one Dwolla Account ID, one merchant destination bank funding source and an injected OAuth bearer-token supplier. MOCK requires a numeric loopback URL. The configured SANDBOX URL must be `https://api-sandbox.dwolla.com`; LIVE must be `https://api.dwolla.com`. Both remain disabled for operations. The host must provide `AuthorizeSource`, which checks the authenticated shopper/order, approved one-time authorization, exact Dwolla customer and funding source, and the durable proof digest before dispatch. The transient `Source` token contains only those IDs and digest, never an account or routing number. The adapter also reads the funding source from Dwolla and requires a verified, nonremoved checking or savings bank with ACH channel before POST. This provider read does not establish customer ownership or legal consent; the host callback must do so. [Funding-source verification](https://developers.dwolla.com/docs/bank-funding-source) · [Retrieve a funding source](https://developers.dwolla.com/docs/api-reference/funding-sources/retrieve-a-funding-source)

The transfer POST uses exact USD decimal value, fixed destination, stable operation `Idempotency-Key`, and operation-ID `correlationId`. Before dispatch, the adapter durably binds the source and destination funding source IDs, operation ID, and amount digest to the reservation. A `201 Location` is followed by a bearer-authenticated transfer GET that must echo the exact transfer ID, source, destination, correlation ID, amount and USD. The resulting Tender payment is **pending with zero authorized, captured or settled funds**. Malformed or lost replies return `ErrUnknownOutcome`; no blind financial POST replay or collection follows. Dwolla's published GET example has empty `_links`, so such a reply is held as unknown until independently resolved. A verified `processed` transfer still stays pending because Dwolla transfers have two-sided legs and can later fail. Read-only `Query` works only when the payment and operation already hold the same transfer ID and the durable source binding matches the authenticated GET. A lost `201` with no persisted reference remains unknown because customer transfer search requires a customer ID absent from the reservation. Capture, void, refund and confirm remain unsupported. [Initiate transfer](https://developers.dwolla.com/docs/api-reference/transfers/initiate-a-transfer) · [Retrieve transfer](https://developers.dwolla.com/docs/api-reference/transfers/retrieve-a-transfer) · [Customer transfer search](https://developers.dwolla.com/docs/api-reference/transfers/list-and-search-transfers-for-a-customer)

`webhook.NewDwolla` validates the original body against `X-Request-Signature-SHA-256`, requires the configured account and transfer resource URL, and inserts an allowlisted event into the durable Tender inbox before HTTP 202. It accepts Dwolla's current `created` timestamp and older documented `timestamp` field. Exact duplicate events are acknowledged; changed evidence under the same event ID conflicts. A signed unrelated customer/funding event is acknowledged without entering the payment inbox because Dwolla subscriptions receive all topics. `Dwolla.Process(ctx, paymentID, eventID)` consumes a signed `transfer_failed`, `customer_transfer_failed`, or `customer_bank_transfer_failed` event only when its resource ID equals the bound payment and operation reference and its correlation ID equals that operation ID. It creates an idempotent **review notice only**; it never changes funds or fulfillment. Other transfer topics and unmatched failed legs remain pending for investigation. The host must poll pending receipts and keep them for review until authenticated transfer and bank evidence can be correlated. [Webhook behavior and HMAC](https://developers.dwolla.com/docs/working-with-webhooks) · [Transfer failures](https://developers.dwolla.com/docs/transfer-failures)

## Open v1 work and qualification

- Persist the customer identity safely so correlation-ID search can resolve a lost `201` without reissuing the POST; an unknown Create remains held today.
- Correlate both transfer legs and return failure reasons with the original operation. A matched failed-event notice is currently review only. Do not infer a settled bank deposit from a `processed` status.
- Define gross, fees, return and payout/bank-statement projection from the selected merchant's authenticated report artifacts. Keep the collection outbox empty until that evidence matches.
- Prove the shopper bank-data boundary and processor/ODFI-approved authorization and retention procedure; collect merchant-owned sandbox transfer, return, webhook and report evidence before any capability is enabled outside MOCK.
