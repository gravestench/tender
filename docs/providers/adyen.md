# Adyen US card checkout

The adapter implements Adyen Checkout **v72** Advanced flow for US/USD Visa and Mastercard. The browser candidate is Adyen Web **6.45.2**. The HTTP contracts use synthetic, loopback fixtures. Credentialed merchant transactions, card-network coverage and browser behavior still need verification. [Checkout v72](https://docs.adyen.com/api-explorer/Checkout/72/overview) · [Adyen Web release](https://github.com/Adyen/adyen-web/releases/tag/v6.45.2) · [Advanced flow](https://docs.adyen.com/online-payments/build-your-integration/advanced-flow/)

## Configure a merchant

Construct `adyen.Config` with the environment, API base, merchant account, server API key, checkout origin and same-origin return URL. Supply the adapter to an engine using provider name `adyen`, the same account and environment, and an exact card market. The adapter disables redirects. An injected RoundTripper must enforce the configured destination and protect request contents.

| Environment | API base |
| --- | --- |
| MOCK | An explicit loopback IP and mount prefix ending in `/v72` |
| SANDBOX | `https://checkout-test.adyen.com/v72` |
| LIVE | The merchant's assigned `https://{prefix}-checkout-live.adyenpayments.com/checkout/v72`, with `LiveActivated` set after merchant approval |

The browser uses the merchant's public client key for an allowed origin. Keep the API key and webhook signing keys on the server. Tender sends `X-API-Key` and the operation's durable `Idempotency-Key` on its POSTs. Use the default random UUID generator or provide globally unique ID/key generation. The adapter accepts alphanumeric characters, underscores and hyphens, up to 57 characters for operation IDs and 64 for provider keys. Adyen scopes keys to the company account and region and retains them for at least seven days. A repeated key can return the first result, including when another merchant account shares that company. Tender rejects a returned idempotency key that differs from the reserved key. [Client-side authentication](https://docs.adyen.com/development-resources/client-side-authentication/) · [Merchant endpoint format](https://docs.adyen.com/development-resources/live-endpoints/) · [Idempotency](https://docs.adyen.com/development-resources/api-idempotency/)

## Prepare the component and submit the payment

1. Call `Engine.Create` for the trusted order, amount and market with an empty token. It calls `POST /paymentMethods` for scheme cards. A successful result contains a `CustomerAction` in component mode. Decode its data as `adyen.CardAction`. For type `card`, configure the Card Component with its specific `Brands`. An unavailable brand returns `ErrUnsupported`. This preparation uses the Advanced flow. The Checkout `/sessions` product has a separate integration path. [Payment methods](https://docs.adyen.com/api-explorer/Checkout/72/post/paymentMethods) · [Card Component](https://docs.adyen.com/payment-methods/cards/web-component/)
2. For `onSubmit`, send the projected `paymentMethod` and `browserInfo` to the authenticated host checkout. The Go host adds the shopper email and trusted client IP and serializes this object as the transient `Engine.Confirm` token. For Visa, collect the holder name in the Component and include the email and IP. Supported card input consists of `type: scheme`, the four JWE fields `encryptedCardNumber`, `encryptedExpiryMonth`, `encryptedExpiryYear` and `encryptedSecurityCode`, and a `brand` matching the host's route (`visa` or `mc`). The host can also supply `checkoutAttemptId` and the holder name as required by the route. Use the component's encrypted fields and ordinary browser info. Keep the card form state out of request logs, instrumentation and storage. [Pinned Card format](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/components/Card/Card.tsx#L143-L172) · [Pinned browser-info fields](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/utils/browserInfo.ts) · [3DS requirements](https://docs.adyen.com/online-payments/3d-secure/api-reference/) · [JWE in Adyen Web](https://docs.adyen.com/online-payments/release-notes?integration_type=web&version=5.20.0)
3. Confirm calls `POST /payments` with the server-owned amount, merchant reference, origin and return URL. It requests manual capture and native 3DS when available. The adapter exposes a direct native `ChallengeShopper` action only when it includes `type: threeDS2`, `subtype: challenge`, `paymentMethodType: scheme`, `token` and `authorisationToken`. After checking the component mode, expiry and `CardAction.Action.Allowed()`, pass the projected action to the pinned SDK. On additional details, submit `{"details":{"threeDSResult":"<opaque component result>"}}` with a fresh host operation key. The adapter binds `/payments/details` to the stored action. [Payment request](https://docs.adyen.com/api-explorer/Checkout/72/post/payments) · [Submit details](https://docs.adyen.com/api-explorer/Checkout/72/post/payments/details) · [Pinned challenge fields](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/components/ThreeDS2/ThreeDS2Challenge.tsx#L49-L68)
4. A recognized native `IdentifyShopper` fingerprint leaves the payment pending with `ProviderStatus == "FingerprintUnavailable"`. Redirects, malformed fingerprints and other unsupported actions report `ActionUnavailable`. Both outcomes carry empty action data. Stop that interaction on the checkout page. The pinned fingerprint flow can call an SDK redirect internally. It stays disabled pending instrumented browser evidence. The direct challenge also needs credentialed browser verification before merchant enablement. [Pinned fingerprint dispatcher](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/components/ThreeDS2/callSubmit3DS2Fingerprint.ts#L95-L101) · [Native 3DS2](https://docs.adyen.com/online-payments/3d-secure/native-3ds2/)
5. Tender accepts an authenticated `Authorised` HTTP response only with its PSP, the original merchant reference, the exact amount and currency, and a `paymentMethod` whose type and actual brand match the configured scheme route. It records that network in `Payment.VerifiedMethod`. Missing or contradictory evidence leaves the outcome unknown. A signed Standard `AUTHORISATION` received first stays pending until the authenticated HTTP evidence is applied. The HMAC omits the card brand. Legacy authorizations without recorded network evidence require manual reconciliation before capture. [v72 payment response](https://docs.adyen.com/api-explorer/Checkout/72/post/payments) · [Standard signed fields](https://docs.adyen.com/development-resources/webhooks/secure-webhooks/verify-hmac-signatures/)


## Capture, cancel and refund

| Engine call | v72 endpoint | Successful Standard event |
| --- | --- | --- |
| Capture | `POST /payments/{paymentPspReference}/captures` | `CAPTURE` |
| Void an open authorization | `POST /payments/{paymentPspReference}/cancels` | `CANCELLATION` |
| Refund captured funds | `POST /payments/{paymentPspReference}/refunds` | `REFUND` |

Each request sends its own merchant reference. Its `received` reply records the payment PSP and modification PSP and leaves that operation pending. A successful authenticated event applies the reserved amount. Partial refunds are supported. Multiple partial captures require both merchant enablement and `MultiplePartialCaptures`. The default configuration accepts full capture. A successful capture or refund notification records the provider's acceptance. A subsequent signed capture failure puts the payment on hold and creates a durable host review item. Refund reversal requires reconciliation. [Manual capture and partial captures](https://docs.adyen.com/online-payments/capture/) · [Cancellation](https://docs.adyen.com/online-payments/cancel/) · [Refunds and reversals](https://docs.adyen.com/online-payments/refund/)

## Receive and process Standard webhooks

Mount `webhook.NewAdyen(webhook.AdyenConfig{Store: db, Engine: engine, Scope: scope, MerchantAccount: account, HMACKeys: keys})` on the host's HTTPS POST endpoint. Supply hex-encoded 256-bit keys dedicated to this account/environment. During rotation both current and previous keys can verify a delivery. The handler checks the expected envelope environment and account, verifies HMAC-SHA256 over each item's eight prescribed fields, and commits only those fields before HTTP 202. Additional data, free-form reason and unsigned timestamps stay out of the evidence. A batch with an invalid signature is rejected before any item is stored. The endpoint accepts up to 32 items and 512 KiB. The merchant references generated by Tender contain no colon or backslash. [Standard HMAC and official vector](https://docs.adyen.com/development-resources/webhooks/secure-webhooks/verify-hmac-signatures/) · [Webhook handling, ordering and duplicates](https://docs.adyen.com/development-resources/webhooks/handle-webhook-events/)

Set `OnStored` to wake a worker promptly. Recover after a crash by selecting the host's pending `tender_provider_events` rows for its scoped provider and account where `processed_at IS NULL`. Pass each `event_id` to `handler.Process(ctx, id)`. The event key includes its code, PSP and digest of signed fields. A replay with changed unsigned metadata maps to the same row. Conflicting signed evidence has its own row for review. Processing resolves the merchant reference against the payment, attempt and operation, checks the amount/currency and PSP references, and updates the receipt, payment, audit and fulfillment outbox in one transaction. Failed processing leaves the receipt pending. [Standard event fields](https://docs.adyen.com/development-resources/webhooks/webhook-types/)

When the event names a modification's merchant reference, the signed callback can resolve a lost HTTP reply. When it names the original payment's merchant reference, the worker also needs the corresponding modification PSP. For an unknown or reserved capture, cancel or refund, call `Engine.Recover(ctx, operationID)` to obtain the cached acknowledgement, then process the pending delivery again. The reservation and each explicit recovery hold a durable dispatch lease for the provider call timeout. A recovery during an active lease returns `ErrConflict` without sending a request. After a lost dispatch or an expired lease, one worker can claim the same key and issue one identical POST. A previous caller's late rejection cannot close that operation. A verified callback that completes during a timed-out replay supplies the returned result. Recovery requires the original method, full endpoint, merchant account, body and provider key recorded by fingerprint at reservation. Its local deadline is 24 hours after reservation. Expired, unbound or differently configured operations require manual reconciliation. A lost `/payments` or `/payments/details` response without trusted network evidence also requires manual review. Advanced-flow `Query` returns `ErrUnsupported`. [Idempotency](https://docs.adyen.com/development-resources/api-idempotency/) · [Checkout endpoint index](https://docs.adyen.com/api-explorer/Checkout/72/overview)

Before capture dispatch, the adapter requires the verified inbox, evidence lookup and durable failure queue on the same transactional store. A hold arriving while a capture, refund or cancel request is in flight preserves the payment hold and its gross history. An authenticated acknowledgement can still bind that operation's PSP for an original-reference callback. A successful cancellation closes its own operation while the payment stays held.

A signed, correlated `CAPTURE_FAILED` fences collection and leaves the payment in `capture_failed`. When the failure was durably received before capture processing, the worker checks it in the same transaction before enqueuing fulfillment. A late failure retains the prior gross capture and collection notice for audit. The host receives one durable review item per capture operation in `tender_capture_failures`. Its worker must check for items even after consuming a prior fulfillment notice, record any compensation or reconciliation work and acknowledge the item transactionally. The hold requires operator review of the capture with Adyen. [Storage and worker queries](../storage.md#recovery-and-host-processing) · [Capture failure and possible recapture](https://docs.adyen.com/online-payments/capture/) · [CAPTURE_FAILED event](https://docs.adyen.com/api-explorer/Webhooks/1/post/CAPTURE_FAILED)

The adapter has no report importer. Additional codes such as `REFUND_FAILED`, `REFUNDED_REVERSED`, `CHARGEBACK` and `EXPIRE` require host review of the verified inbox and provider reports. Settlement evidence and handling of those corrections are outstanding before a production pilot. [Event definitions](https://docs.adyen.com/development-resources/webhooks/webhook-types/) · [Refund failure](https://docs.adyen.com/online-payments/refund/)

The offline simulator is `mockserver.AdyenRoutes`. Its scripted action tokens, PSP references and notification timing are synthetic. Its wire shapes follow the pinned API and Standard webhook documentation. The published HMAC example independently checks the verifier. Run `go test -tags=integration ./test/contract -run '^TestAdyen'`, with `TENDER_TEST_DATABASE_URL` set to a disposable local database to exercise the PostgreSQL subtest.
