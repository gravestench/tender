# Adyen US card checkout

The adapter implements Adyen Checkout **v72** Advanced flow for US/USD Visa and Mastercard. The browser candidate is Adyen Web **6.45.2**. The HTTP contracts use synthetic, loopback fixtures. Credentialed merchant transactions, card-network coverage and browser behavior still need verification. [Checkout v72](https://docs.adyen.com/api-explorer/Checkout/72/overview) · [Adyen Web release](https://github.com/Adyen/adyen-web/releases/tag/v6.45.2) · [Advanced flow](https://docs.adyen.com/online-payments/build-your-integration/advanced-flow/)

## Configure a merchant

Construct `adyen.Config` with the environment, API base, merchant account, server API key, checkout origin and same-origin return URL. Supply the adapter to an engine using provider name `adyen`, the same account and environment, and an exact card market. The adapter disables redirects. An injected RoundTripper must enforce the configured destination and protect request contents.

| Environment | API base |
| --- | --- |
| MOCK | An explicit loopback IP and mount prefix ending in `/v72` |
| SANDBOX | `https://checkout-test.adyen.com/v72` |
| LIVE | The merchant's assigned `https://{prefix}-checkout-live.adyenpayments.com/checkout/v72`, with `LiveActivated` set after merchant approval |

The browser uses the merchant's public client key for an allowed origin. Keep the API key and webhook signing keys on the server. Tender sends `X-API-Key` and the operation's durable `Idempotency-Key` on its POSTs. Use the default random UUID generator or provide globally unique ID/key generation. The adapter accepts alphanumeric characters, underscores and hyphens, up to 57 characters for operation IDs and 64 for provider keys. The provider's request deduplication window is finite and regional. [Client-side authentication](https://docs.adyen.com/development-resources/client-side-authentication/) · [Merchant endpoint format](https://docs.adyen.com/development-resources/live-endpoints/) · [Idempotency](https://docs.adyen.com/development-resources/api-idempotency/)

## Prepare the component and submit the payment

1. Call `Engine.Create` for the trusted order, amount and market with an empty token. It calls `POST /paymentMethods` for scheme cards. A successful result contains a `CustomerAction` in component mode. Decode its data as `adyen.CardAction`. For type `card`, configure the Card Component with its specific `Brands`. An unavailable brand returns `ErrUnsupported`. This preparation uses the Advanced flow. The Checkout `/sessions` product has a separate integration path. [Payment methods](https://docs.adyen.com/api-explorer/Checkout/72/post/paymentMethods) · [Card Component](https://docs.adyen.com/payment-methods/cards/web-component/)
2. For `onSubmit`, send the projected `paymentMethod` and `browserInfo` to the authenticated host checkout. The Go host adds the shopper email and trusted client IP and serializes this object as the transient `Engine.Confirm` token. For Visa, collect the holder name in the Component and include the email and IP. Supported card input consists of `type: scheme`, the four JWE fields `encryptedCardNumber`, `encryptedExpiryMonth`, `encryptedExpiryYear` and `encryptedSecurityCode`, plus optional `brand`, `holderName` and `checkoutAttemptId`. Use the component's encrypted fields and ordinary browser info. Keep the card form state out of request logs, instrumentation and storage. [Pinned Card format](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/components/Card/Card.tsx#L143-L172) · [Pinned browser-info fields](https://github.com/Adyen/adyen-web/blob/v6.45.2/packages/lib/src/utils/browserInfo.ts) · [3DS requirements](https://docs.adyen.com/online-payments/3d-secure/api-reference/) · [JWE in Adyen Web](https://docs.adyen.com/online-payments/release-notes?integration_type=web&version=5.20.0)
3. Confirm calls `POST /payments` with the server-owned amount, merchant reference, origin and return URL. It requests manual capture and native 3DS when available. Tender exposes only `threeDS2` fingerprint or challenge actions in component mode, using a ten-minute local action lifetime. Pass only `CardAction.Action` to the pinned SDK after checking the mode and expiry. On additional details, submit `{"details":{"threeDSResult":"<opaque component result>"}}` with a fresh host operation key. The adapter binds `/payments/details` to the stored action and checks the provider's echoed merchant reference or already-bound PSP reference. [Payment request](https://docs.adyen.com/api-explorer/Checkout/72/post/payments) · [Submit details](https://docs.adyen.com/api-explorer/Checkout/72/post/payments/details) · [Native 3DS2](https://docs.adyen.com/online-payments/3d-secure/native-3ds2/)
4. A redirect or unrecognized action yields a pending payment with `ProviderStatus == "ActionUnavailable"` and empty action data. Stop that interaction on the checkout page. The reservation stays open pending authoritative resolution. A refusal records a declined payment. An authorization records authorized funds. The host can display current state using `Engine.Get`. The SDK's native challenge UX, its own fallback behavior and issuer requirements need an instrumented credentialed browser test before merchant enablement. [Action handling](https://docs.adyen.com/online-payments/3d-secure/native-3ds2/) · [Result codes](https://docs.adyen.com/online-payments/build-your-integration/payment-result-codes/)

## Capture, cancel and refund

| Engine call | v72 endpoint | Successful Standard event |
| --- | --- | --- |
| Capture | `POST /payments/{paymentPspReference}/captures` | `CAPTURE` |
| Void an open authorization | `POST /payments/{paymentPspReference}/cancels` | `CANCELLATION` |
| Refund captured funds | `POST /payments/{paymentPspReference}/refunds` | `REFUND` |

Each request sends its own merchant reference. Its `received` reply records the payment PSP and modification PSP and leaves that operation pending. A successful authenticated event applies the reserved amount. Partial refunds are supported. Multiple partial captures require both merchant enablement and `MultiplePartialCaptures`. The default configuration accepts full capture. A successful capture or refund notification records the provider's acceptance. Subsequent scheme failure or reversal requires reconciliation. [Manual capture and partial captures](https://docs.adyen.com/online-payments/capture/) · [Cancellation](https://docs.adyen.com/online-payments/cancel/) · [Refunds and reversals](https://docs.adyen.com/online-payments/refund/)

## Receive and process Standard webhooks

Mount `webhook.NewAdyen(webhook.AdyenConfig{Store: db, Engine: engine, Scope: scope, MerchantAccount: account, HMACKeys: keys})` on the host's HTTPS POST endpoint. Supply hex-encoded 256-bit keys dedicated to this account/environment. During rotation both current and previous keys can verify a delivery. The handler checks the expected envelope environment and account, verifies HMAC-SHA256 over each item's eight prescribed fields, and commits only those fields before HTTP 202. Additional data, free-form reason and unsigned timestamps stay out of the evidence. A batch with an invalid signature is rejected before any item is stored. The endpoint accepts up to 32 items and 512 KiB. The merchant references generated by Tender contain no colon or backslash. [Standard HMAC and official vector](https://docs.adyen.com/development-resources/webhooks/secure-webhooks/verify-hmac-signatures/) · [Webhook handling, ordering and duplicates](https://docs.adyen.com/development-resources/webhooks/handle-webhook-events/)

Set `OnStored` to wake a worker promptly. Recover after a crash by selecting the host's pending `tender_provider_events` rows for its scoped provider and account where `processed_at IS NULL`. Pass each `event_id` to `handler.Process(ctx, id)`. The event key includes its code, PSP and digest of signed fields. A replay with changed unsigned metadata maps to the same row. Conflicting signed evidence has its own row for review. Processing resolves the merchant reference against the payment, attempt and operation, checks the amount/currency and PSP references, and updates the receipt, payment, audit and fulfillment outbox in one transaction. Failed processing leaves the receipt pending. [Standard event fields](https://docs.adyen.com/development-resources/webhooks/webhook-types/)

For modifications, a signed modification reference can resolve a lost HTTP reply. When the event names the original payment's merchant reference, resolution also needs the corresponding modification PSP bound by the HTTP reply. Missing or contradictory identity stays pending for a later correlation or manual reconciliation. Tender does not guess which equal-sized capture or refund was intended. The host can inspect its current order and processor records. Advanced-flow payments have no general Checkout payment-status GET. `Query` and `Engine.Recover` return `ErrUnsupported`. This adapter has no report importer. Additional codes such as `CAPTURE_FAILED`, `REFUND_FAILED`, `REFUNDED_REVERSED`, `CHARGEBACK` and `EXPIRE` require host review of the verified inbox and provider reports. Settlement and post-acceptance corrections are outstanding before a production pilot. [Checkout endpoint index](https://docs.adyen.com/api-explorer/Checkout/72/overview) · [Event definitions](https://docs.adyen.com/development-resources/webhooks/webhook-types/) · [Refund failure](https://docs.adyen.com/online-payments/refund/)

The offline simulator is `mockserver.AdyenRoutes`. Its scripted action tokens, PSP references and notification timing are synthetic. Its wire shapes follow the pinned API and Standard webhook documentation. The published HMAC example independently checks the verifier. Run `go test -tags=integration ./test/contract -run '^TestAdyen'`, with `TENDER_TEST_DATABASE_URL` set to a disposable local database to exercise the PostgreSQL subtest.
